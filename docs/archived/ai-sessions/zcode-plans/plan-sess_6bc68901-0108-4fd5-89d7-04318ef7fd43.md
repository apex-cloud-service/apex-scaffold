### 整改方式（按你选定的"彻底整改"）

**统一模式：单一 Spring 构造器 + 静态工厂供测试**

1. **10 个 `@Autowired` 类**：删除注解与 import；Spring 构造器保持 `public` 为**唯一 public 构造器**，其余构造器改为 `private` + `static` 工厂方法（命名 `forTesting(...)` / `withClient(...)` 等语义化名称），或直接用 `@VisibleForTesting` 风格静态工厂。
   - 对只有 1 个构造器的类（#2、#3、#4、#7 中的部分），直接删注解即可（Spring 自动选用唯一构造器）。
   - 对 `OpenAppAdminService`：删除 `@Deprecated` 过渡构造器（无生产调用点，仅 1 处测试），测试改用静态工厂或主构造器。
2. **2 处 MapStruct `@Resource`**：改用 `JsonUtil.getObjectMapper()`（`apex-common` 已提供静态线程安全实例，`apex-office` 已依赖 `apex-common`），删除 `@Resource` 与字段默认 `new ObjectMapper()`。这样转换器完全脱离容器，单测也可用。
3. **测试侧适配**：更新 7 个测试文件的构造调用点（`IdentityRelayAuthenticationFilterTest` × 4、`MessageWebSocketTest`、`MessageDatabaseWebSocketTest`、`MessageGatewayDatabaseIntegrationTest`、`ClientTierClientTest`、`OpenApiScopeGatewayFilterTest`、`GatewayJwtVerifierServiceTest`、`ChunkUploadServiceTest`、`OpenAppAdminServiceTest`）。
4. **防回归**：新增 `NoAutowiredArchTest`（参照 `apex-system/.../arch/NoBoundedElasticArchGuardTest.java` 的写法，用文件遍历 + 正则），扫描全仓 `src/main/java`，断言无 `@Autowired`/`@Resource` 字段注入。放在 `apex-system/src/test/.../arch/`。
5. **保留例外**：测试代码 `@Resource` 注入 `WebTestClient`（`@WebFluxTest` 限制）保留，并在测试 Javadoc 说明。

### 确认的缺口（需新增迁移）

**缺口 A（高）：`apex-auth-service` 生产库 `apex_auth` 缺 3 张表**

auth 域代码用 R2DBC 直接访问，但 `apex-auth-service/src/main/resources/db/migration/{mysql,postgresql}` 中**完全没有**建表语句；这些表只存在于 `apex-system` 迁移（`V53__ip_access_control.sql`、`V55__biometric_auth.sql`、`V56__device_trust.sql`）和 auth 的 `basic-schema.sql`（仅 basic/H2 档）。

证据：
- `IpAccessControlFilter` 在 `AuthCenterConfig.java:109` 被注册为 `@Bean`，`@Order(-100)` 对**每个请求**执行，内部 `IpAccessControlServiceImpl.isAccessAllowed()` 查询 `ip_access_control`；表不存在时 `onErrorResume` 返回 `false` → **全部非白名单路径请求 403**。生产库 `apex_auth`（`podman-compose.yml:220`）没有这张表。
- `BiometricAuthServiceImpl`、`DeviceTrustServiceImpl`、`BiometricAuthRepository`、`DeviceTrustRepository`、`MfaConfigRepository`（`@Table("mfa_config")`）均无对应迁移。
- 注意：`jwt_keys`（`JwtKeyEntity`）虽在 auth 有 `JwtKeyRepositoryImpl`，但**无任何注入点**，且 `JwtKeyRotationService` 实际用 Redis；`oauth2_registered_client` 属 system 域（OAuth2 客户端配置在 `auth_config`）——这两张表**不补**。

**整改**：新增 `apex-auth-service/src/main/resources/db/migration/{mysql,postgresql}/V62__create_auth_security_tables.sql`，按 auth 实体字段建 `ip_access_control`、`biometric_auth`、`device_trust`、`mfa_config` 四表（`mfa_config` 需保留，`MfaConfig` 实体在用）。字段以实体为准；`IpAccessControl` 有 `created_by NOT NULL`，DDL 需对应。两方言语义对齐。

**缺口 B（中）：`sys_user.email` 两方言长度不一致**

- MySQL：`V37` 建 `VARCHAR(100)` → `V51` 动态改为 `VARCHAR(255)` + `idx_email`
- PG：`V37` 建 `VARCHAR(100)`，`V43` 建索引，但**从未改到 255**（`V62` 只改 `keycloak_sub`）

**整改**：PG 侧在 system 域追加 `V89__align_sys_user_email_length.sql`，`ALTER TABLE sys_user ALTER COLUMN email TYPE VARCHAR(255)`。MySQL 侧已有 255 无需变更（但为版本配对，MySQL 也需一个同版本空操作/幂等脚本；按项目既有做法可写 `V89` 配对脚本，注释说明）。

**缺口 C（低）：PG V51–V58 占位脚本的注释与 MySQL 实际内容不符**

PG `V51__mysql_alignment_placeholder.sql` 声称"对应 mysql/V51__add_keycloak_fields.sql"，但实际 keycloak 字段在 PG 由 V37/V62 覆盖，注释描述正确；V52/V55/V56/V58 同构。仅需核对注释准确性，若已准确则不动。

**缺口 D（低）：`apex-auth-service/basic-schema.sql` 与 Flyway 漂移**

basic-schema 有 18 表，Flyway 有 18 表（含 `auth_password_recovery`），但 basic-schema **缺 `auth_password_recovery`**（grep 计数 0）。basic/H2 档启动后密码找回功能不可用。

**整改**：在 `apex-auth-service/src/main/resources/db/basic-schema.sql` 补 `auth_password_recovery` 表。

**验证**：新增/扩展测试——
- 在 `apex-auth-service` 增加类似 `OfficeFlywayMigrationTest` 的 PO↔DDL 静态校验（反射读 `@Table`/`@TableName` 字段 → 断言列存在，两方言列集合一致）。
- 已有 `FlywayMigrationVersionTest`（system）会强制 MySQL/PG 版本连续一致，新增 V89 后必须两方言同时加。
