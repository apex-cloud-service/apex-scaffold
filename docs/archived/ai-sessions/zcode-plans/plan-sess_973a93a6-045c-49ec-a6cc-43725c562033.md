# 方案:新增 apex-tools-build 构建发布管理模块

## 一、背景与可行性结论

**结论:可行**,但需接受一个 Maven 固有限制:reactor 内的模块无法编排"包含它自己的那次构建"(鸡生蛋)。因此"管理"能力拆成两层实现:

1. **reactor 内(受门禁保护)**:模块注册表 + 防漂移一致性测试,进入 `mvnd verify` 常规门禁;
2. **reactor 外(统一入口)**:`bin/apex.sh` 由人/CI 调用,编排现有 `mvnd`、`scripts/build/build.sh`、`scripts/release/release.sh`、`scripts/deploy/*` 等已验证执行器。

与现有 `apex-tools-deployment`(in-reactor 工具模块、reactor 外被脚本调用)完全同构,有先例可循。

**现状痛点(探索确认)**:构建环境/构建/打包/部署散落在 8 个入口(init-build-env.sh、build.sh、release.sh、start.sh/stop.sh、pull-infra-images.sh、local-deployment.sh、app.sh),无统一生命周期入口;`security-key-check` 所需的 `tools/local-deployment.jar` 无自动补建编排;34 个模块清单、7 个服务交付 JAR 集合、各服务 mainClass/端口等事实无机器可校验的单一注册表,漂移只能靠人工核对。

## 二、总体设计

### 新模块 `apex-tools-build`(第 35 号模块,parent=根 POM,packaging=jar)

```
apex-tools-build/
├── pom.xml                                # 直接 parent 根 POM;零生产依赖
│                                          # test scope: junit-jupiter + snakeyaml(父 BOM 已管版本)
├── bin/apex.sh                            # 统一生命周期入口(zsh;set -euo pipefail;
│                                          #   source scripts/lib/common.sh 复用 log_*/require_command/get_project_root)
├── src/main/resources/build-manifest.yaml # 35 模块注册表(单一事实来源)
├── src/test/java/com/apex/scaffold/tools/build/
│   ├── BuildManifestSyncTest.java         # 防漂移三方一致性测试(进 verify 门禁)
│   └── (如需)ReleaseScriptContractTest    # release.sh SERVICES 数组格式契约
└── README.md                              # 模块说明 + apex.sh 命令手册
```

### build-manifest.yaml(模块注册表)

每个模块一条记录:`artifactId`、`category`(共享基础/共享设施/共享契约/业务库/运行模块/服务增强/组合部署/工具/构建管理)、`deliverable`(`none`|`service-jar`|`tool-jar`|`optional`)、`mainClass`(可执行模块)、`port`(信息性)。纯资源文件,不进任何服务的运行期装配。

### BuildManifestSyncTest(核心防漂移门禁,仿 `FlywayMigrationVersionTest` 模式)

- 根 `pom.xml` 的 `<modules>` 集合 == 注册表 artifactId 集合(35=35);
- 每个 `deliverable=service-jar` 模块:其子 POM 含 spring-boot-maven-plugin 且 `mainClass` 与注册表一致(JDK 内置 DOM 解析,零新依赖);
- `scripts/release/release.sh` 的 `SERVICES` 数组 == 注册表 `service-jar` 集合(网关+6 业务服务,共 7 个)——锁死"发布脚本 vs POM vs 注册表"三方一致。

测试为纯 JVM 断言,不执行 shell,不依赖本机环境(CI 可跑)。

### bin/apex.sh 子命令(全部委托现有执行器,不重写其逻辑)

| 子命令 | 行为 | 委托/说明 |
| --- | --- | --- |
| `env` | 加载并校验构建环境,打印 JDK/mvnd 版本 | source `scripts/build/init-build-env.sh` |
| `build [-P profile] [--module X..] [--with-tests]` | 整仓默认走 build.sh;`--module` 时 `mvnd -pl <列表> -am clean package` | 必带 `-am`(项目经验) |
| `test [--module X]` | `mvnd -pl X -am test` | 快速验证 |
| `verify` | `mvnd -T4 -B clean verify` | 完整门禁 |
| `package [-P profile]` | 构建 7 个服务 fat jar 并逐一校验"有且仅有一个发布 JAR" | 模块列表来自注册表 `service-jar` |
| `release [basic\|standard\|enterprise] [版本]` | 发布前置检查(工作区干净、版本与 POM 一致)→ 执行 release.sh → 校验 `.zip` 与 `.zip.sha256` 生成 | 委托 `scripts/release/release.sh`,不改动它 |
| `image build [--module X\|--all] [--mode prebuilt\|source]` | `podman build -f Containerfile`,注入 SERVICE_MODULE/BUILD_MODE/BUILD_VERSION(读根 POM) | 补齐镜像构建无统一入口的缺口 |
| `deploy precheck` | podman/podman-compose 存在性;`.env` 存在性(缺失提示 cp .env.example);`tools/local-deployment.jar` 缺失时自动 `mvnd -pl apex-tools-deployment -am package -DskipTests` 补建并复制 | 修复"security-key-check JAR 无编排"缺口 |
| `deploy infra` | 拉取基础设施镜像 + 起基础设施栈 | 委托 `pull-infra-images.sh` + `podman-compose.infra.yml up -d` |
| `deploy up [--profile ..]` / `deploy down` | 主栈起停 | 委托 `scripts/deploy/start.sh` / `stop.sh` |
| `deploy status` / `deploy health` | compose ps / 7 服务 readiness 轮询(curl,端口取注册表) | 新增健康检查聚合 |
| `status` | 环境版本 + 注册表概览 + 各模块 target 产物存在性 | — |
| `help` | 子命令手册 | — |

## 三、明确边界(不做的事)

- **不搬移、不重写**任何现有脚本;build.sh/release.sh/app.sh 等保持原样作为底层执行器,`bin/apex.sh` 只做编排层;
- **部署管理 = 本机 Podman Compose + 离线包编排**;不含 SSH 远程部署、不含 k8s apply 自动化(清单仍为 apply 前手工修改 Secret/Ingress);
- **不改发布包内容**:release.sh 产物结构不动(仅被一致性测试读取,脚本头会加注释说明该契约);
- **不动 `.github/workflows/ci-cd.yml`**:其旧 release job 与 release.yml 双路径漂移属既有问题,本战役仅在新模块文档"已知问题"记录,留待后续;
- 不引入 SSH 工具、不新增远程凭据管理;新模块不打进交付包。

## 五、验证门禁

```bash
source scripts/build/init-build-env.sh
mvnd -pl apex-tools-build -am test          # 新模块单测(必带 -am)
mvnd -T4 -B spotless:check                   # 含新模块格式门禁
./apex-tools-build/bin/apex.sh env           # 冒烟:环境校验
./apex-tools-build/bin/apex.sh status        # 冒烟:注册表渲染
./apex-tools-build/bin/apex.sh deploy precheck   # 冒烟:工具 JAR 补建逻辑(不执行容器操作)
./apex-tools-build/bin/apex.sh build --module apex-common   # 真实构建冒烟
mvnd -T4 -B clean verify                     # 完整回归(~20 分钟,含新一致性测试)
git diff --check
```

预期:`BUILD SUCCESS`、`Failures: 0 / Errors: 0`;`deploy up/infra` 等真实容器操作不在本战役冒烟(需本机 podman 环境与 `.env` 密钥),如实报告未验证项。
