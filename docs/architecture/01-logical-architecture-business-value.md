# Apex Scaffold DDD 四层逻辑架构商业价值说明

> 本文描述架构带来的可验证工程价值，不将未经测量的性能、成本、ROI 或客户数据作为事实。

![Apex Scaffold DDD 四层逻辑架构图](../diagrams/01_logical_architecture.svg)

## 1. 价值主张

Apex Scaffold 通过 DDD 四层架构把业务能力与数据库、缓存、消息、存储和外部服务实现分离，使同一套领域与应用能力能够面向不同客户环境进行组合、替换和治理。

其商业价值不在于抽象层数量，而在于降低定制交付对核心业务代码的侵入，并让安全、监控、数据和集成能力具有明确的维护边界。

## 2. 面向客户的能力

| 客户关注点       | 架构支撑                                   | 可验收证据                      |
| ----------- | -------------------------------------- | -------------------------- |
| 能否按规模选择功能   | `basic`、`standard`、`enterprise` 构建档位   | 根 POM 的 Profile 与产物配置      |
| 能否适配既有基础设施  | 领域端口与基础设施适配器                           | Repository 接口及其 `*Impl` 实现 |
| 能否替换对象存储    | Local、MinIO、火山云 TOS 实现                 | Storage Service 实现与条件配置    |
| 能否控制数据与权限边界 | JWT、RBAC、租户上下文、权限切面                    | 安全配置、权限注解、租户处理代码           |
| 能否观测运行状态    | Actuator、Micrometer、Prometheus、日志与追踪能力 | 监控配置、指标端点和 Dashboard 配置    |
| 能否持续保持架构质量  | ArchUnit 分层与事务规则                       | `LayeringArchTest` 自动化测试   |

## 3. 对交付效率的影响

### 3.1 降低定制侵入

客户需要更换数据库访问策略、缓存、对象存储、短信渠道或搜索引擎时，优先新增或替换基础设施适配器。只要领域端口保持稳定，应用用例和接口契约无需同步大范围改写。

验收方式：统计定制需求涉及的模块数量、核心领域文件变更数量及回归测试范围。

### 3.2 提升问题定位效率

四层职责为故障分类提供直接路径：协议和鉴权问题定位接口层，用例编排定位应用层，业务不变量定位领域层，SQL、缓存、消息和第三方调用定位基础设施层。

验收方式：记录缺陷首次定位耗时、跨模块误改次数和同类故障复发率。

### 3.3 支持能力分档

构建 Profile 将 JWT、RBAC、缓存、消息、监控和追踪划分为不同组合。该机制可支撑基础交付、标准交付和企业交付，但商业授权、发布物剥离和运行配置仍需配套发布流程验证。

验收方式：对各 Profile 执行构建、依赖清单、条件 Bean 和启动测试，确认功能边界与销售口径一致。

## 4. 对产品质量的影响

### 4.1 可测试性

领域模型和端口不绑定 Web、MyBatis-Plus 或具体 SDK，可用单元测试验证业务规则；基础设施适配器可独立进行数据库、缓存和外部服务集成测试。

### 4.2 可维护性

新增功能时有稳定的代码落点，评审者可以依据模块边界判断职责是否放置正确。ArchUnit 将部分架构约束自动化，减少仅依靠人员记忆造成的漂移。

### 4.3 可替换性

仓储、缓存、对象存储、消息和搜索通过端口或适配器隔离。可替换性是否成立，应通过契约测试或替代实现测试验证，不能只依据接口数量判断。

### 4.4 风险隔离

第三方 SDK、网络重试、超时、认证和日志细节下沉到基础设施层，减少外部变化扩散到领域模型的范围。WebFlux 与阻塞 I/O 的边界规则降低事件循环被阻塞的运行风险。

## 5. 商业化包装建议

| 交付档位 | 建议定位           | 默认能力事实                    |
| ---- | -------------- | ------------------------- |
| 基础版  | 小型项目或最小运行基线    | JWT 开启；RBAC、缓存、消息、监控、追踪关闭 |
| 标准版  | 常规企业后台与业务系统    | JWT、RBAC、缓存、监控开启；消息和追踪关闭  |
| 企业版  | 需要消息与链路追踪的复杂环境 | 六类能力全部开启                  |

上述矩阵来自 Maven Profile，不等同于完整的商务授权清单。正式报价或合同应另外明确：支持范围、SLA、部署拓扑、外部组件费用、升级服务和定制边界。

## 6. 可量化指标体系

在没有真实基线数据前，不填写预设提升百分比。建议在试点和正式交付中持续采集：

| 价值维度 | 指标                     | 数据来源               |
| ---- | ---------------------- | ------------------ |
| 交付效率 | 从需求确认到可验收版本的周期         | 项目管理与发布记录          |
| 定制成本 | 单项定制涉及模块数、修改文件数、测试数    | Git 变更与 CI 报告      |
| 架构质量 | ArchUnit 违规数、跨层依赖数     | 测试报告、静态分析          |
| 可靠性  | 错误率、恢复时间、下游超时率         | Prometheus、日志、告警记录 |
| 性能   | 吞吐、P95/P99 延迟、阻塞线程池饱和度 | 压测与监控数据            |
| 运维效率 | 告警到定位时间、发布失败率、回滚次数     | 告警与发布平台            |
| 可替换性 | 适配新基础设施所需变更范围          | 适配项目复盘             |

ROI 应在取得实际数据后计算：

```text
ROI =（可归因收益 - 实施与运维总成本）/ 实施与运维总成本
```

可归因收益必须有明确口径，例如减少的交付人日、避免的重复开发成本或缩短的故障恢复时间。

## 7. 风险与控制

| 风险              | 影响        | 控制措施                           |
| --------------- | --------- | ------------------------------ |
| 分层过度导致简单需求变慢    | 增加文件与转换成本 | 复用既有模式，只在存在业务语义时引入领域抽象         |
| 文档能力与默认部署不一致    | 销售和交付预期偏差 | 所有方案标明 Profile、配置状态和外部依赖       |
| WebFlux 与阻塞组件混用 | 延迟抖动或线程耗尽 | 专用调度器、连接池指标、超时与压力测试            |
| 端口只形式化、实现不可替换   | 替换时仍需修改上层 | 增加契约测试并实际验证至少一种替代实现            |
| 多模块出现隐式反向依赖     | 架构逐步失效    | ArchUnit、Maven 依赖检查和代码评审门禁     |
| 商业指标未经验证        | 决策失真      | 禁止在材料中使用无来源的 QPS、SLA、ROI 和案例数据 |

## 8. 客户验收建议

1. 选择一个真实业务用例，从 Router 追踪到基础设施实现，验证分层链路。
2. 在不修改领域和应用代码的前提下切换一个可插拔基础设施能力。
3. 分别构建并启动目标 Profile，核对功能与依赖清单。
4. 执行 ArchUnit、模块测试和关键接口测试。
5. 在目标环境执行容量测试，建立吞吐、延迟和资源基线。
6. 验证监控、日志、告警和故障定位流程。

## 9. 结论

该架构适合作为多能力企业脚手架的长期基础，因为它将业务资产、交付入口和技术实现划分为可治理边界。其价值应通过变更范围、测试结果、交付周期和运行数据持续证明，而不是通过未经验证的宣传数字表达。
