# ADR-001：采用 DDD 四层架构与依赖倒置

- 状态：已采纳

- 决策日期：2026-09-04（文档化日期）

- 适用范围：Apex Scaffold 后端核心模块

- 项目基线：根 POM `1.2.0`

![Apex Scaffold DDD 四层逻辑架构图](../diagrams/01_logical_architecture.svg)

## 1. 决策摘要

Apex Scaffold 使用接口层、应用层、领域层和基础设施层组织后端代码。业务模型与技术实现通过领域端口解耦，基础设施适配器实现领域端口，源码依赖遵循：

```text
Interfaces -> Application -> Domain <- Infrastructure
```

通过多 Maven 模块表达物理边界，并使用 ArchUnit 对关键源码依赖规则进行自动化校验。

## 2. 背景

脚手架同时覆盖认证授权、组织权限、工作流、文件存储、缓存、消息、搜索、外部服务和监控等能力。若按 Controller、Service、Mapper 的简单技术分层持续扩展，容易出现以下问题：

- 业务规则散落在 Handler、Service 和 Mapper 中。

- 应用服务直接绑定 MyBatis、Redis、对象存储或消息客户端。

- 替换基础设施时影响上层业务用例。

- WebFlux 与阻塞数据访问边界不清晰。

- 不同商业档位难以按能力组合和裁剪。

## 3. 决策目标

- 保持核心业务模型独立于 Web 和基础设施框架。

- 为数据库、缓存、消息、存储、搜索及第三方服务提供可替换端口。

- 支持多模块并行开发和架构规则自动校验。

- 让基础版、标准版、企业版共享领域模型，并通过配置组合技术能力。

- 明确响应式协议层与阻塞基础设施之间的调度和事务边界。

## 4. 候选方案

### 方案 A：单模块传统三层架构

以 Controller、Service、Mapper 分包，所有技术依赖集中在一个可执行模块。

优点：结构直接，初期开发成本低。\
缺点：边界主要依靠约定，业务与技术耦合会随功能增长而加重，不适合脚手架的可裁剪和可替换目标。

### 方案 B：DDD 四层多模块架构

领域层定义模型与端口，应用层编排用例，接口层适配协议，基础设施层实现技术端口。

优点：业务边界清晰，可替换性和可测试性较好，适合多业务域和多基础设施实现。\
缺点：模块和对象转换更多，需要团队持续维护依赖纪律。

### 方案 C：全面微服务拆分

按业务域拆成独立服务，使用注册中心、网关和消息系统协作。

优点：独立部署和扩缩容能力强。\
缺点：在业务边界、团队规模和运行负载尚未证明前，会显著增加部署、数据一致性、可观测性和运维复杂度。

## 5. 决策

选择方案 B，并保留未来按稳定业务边界拆分微服务的可能性。

当前项目是模块化单体优先：通过 Maven 模块和领域端口获得清晰边界，同时避免过早引入分布式系统成本。Nacos、RocketMQ、Sentinel 和链路追踪等能力可用于企业档位或后续演进，但其存在不改变当前逻辑分层原则。

## 6. 关键约束

1. `apex-domain` 不依赖 `interfaces`、`infrastructure` 或 MyBatis-Plus。
2. `apex-application` 生产代码不导入 `interfaces` 或 `infrastructure` 包。
3. `apex-infrastructure` 不依赖 `interfaces`。
4. Repository 和技术能力契约优先定义在领域层，实现位于基础设施层。
5. Handler 保持薄层，业务用例进入应用服务。
6. 普通 JDBC `@Transactional` 不用于返回 `Mono`/`Flux` 的方法。
7. 阻塞 I/O 必须从 Netty 事件循环隔离。
8. 能力启用状态由构建档位与运行配置共同决定。

以上第 1、2、3、6 项已在 `LayeringArchTest` 中形成自动化规则。

## 7. 结果与影响

### 正向影响

- 领域模型可以脱离数据库和 Web 框架进行测试。

- MySQL、Redis、对象存储、搜索和消息能力可通过适配器演进。

- 功能定位与代码评审标准更明确。

- 架构边界可由测试持续验证，而非仅依赖文档。

- 不同产品档位可共享业务代码并裁剪基础设施能力。

### 成本与约束

- DTO、领域对象和 PO 之间需要明确转换。

- 简单 CRUD 也必须遵守层次边界，文件数量会增加。

- 团队需要理解控制流与依赖方向的区别。

- WebFlux 配合阻塞持久化需要专门的调度、事务和监控策略。

- 架构图与实现必须持续同步，否则图中的能力全集容易被误解为默认部署状态。

## 8. 已知偏差与技术债

- `apex-application/pom.xml` 当前声明 `apex-infrastructure` 依赖，但 ArchUnit 禁止应用源码导入基础设施包。应检查该依赖是否仅为历史或测试/装配需要，并在可行时移除或调整作用域。

- 图中的 GraphQL、gRPC、WebSocket 等入口属于能力或扩展方向，不能仅凭图表认定生产环境已开放。

- RocketMQ 和链路追踪在依赖层面具备支持，但默认 `standard` Profile 分别关闭消息队列和追踪。

- 运行性能、容量和可用性必须由目标环境压测与监控数据确认。

## 9. 合规验证

架构变更至少应验证：

- ArchUnit 分层规则。

- 受影响模块的单元与集成测试。

- Router、Handler、权限和 OpenAPI 的一致性。

- 阻塞 I/O 调度和 JDBC 事务边界。

- Flyway 迁移的可重复部署性。

- 条件 Bean 在 `basic`、`standard`、`enterprise` 下的装配结果。

## 10. 重新评估条件

出现以下情况时重新评估本决策：

- 某业务域需要独立发布、扩缩容或独立数据治理。

- 模块间同步调用和共享数据库成为主要交付瓶颈。

- Maven 模块无法有效阻止跨边界耦合。

- 响应式协议层与阻塞基础设施的复杂度超过其收益。

- 商业档位需要完全独立的产物或插件生态。
