# Apex Scaffold 业务代码与功能增强需求方案

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档名称 | Apex Scaffold 业务代码与功能增强需求方案 |
| 方案状态 | 已确认，实施中 |
| 适用对象 | 通用后端开发脚手架、企业管理系统、SaaS 管理平台、私有化项目 |
| 目标市场 | 中国企业客户优先 |
| 当前基线 | 当前仓库可见代码、配置、示例、生成器和部署资产 |
| 执行原则 | 方案确认前只评审和设计，不修改业务代码 |

## 2. 编制目的

当前项目已经具备较完整的后端基础设施，包括认证授权、统一响应、参数校验、缓存、限流熔断、消息、审计、监控、文件存储、代码生成和部署资产。

本方案只针对仍影响商业交付和业务开发效率的增强项，重点解决以下问题：

1. 客户拿到脚手架后，能否快速创建真实业务模块。
2. 常见企业管理场景能否直接复用，而不是每个项目重新设计。
3. 系统管理、组织权限、租户、字典、配置、任务和审计能否形成完整闭环。
4. 生成的业务代码能否直接编译、迁移、启动和验收。
5. 多租户、数据权限、幂等、状态流转、批量操作和导入导出是否具备统一业务规范。
6. 业务代码是否可以在不破坏 DDD、WebFlux 和模块边界的前提下持续扩展。

## 3. 当前能力与本方案边界

### 3.1 当前已具备、原则上不重复建设的能力

以下能力已经在仓库中存在，本方案只要求补充业务接入规范、覆盖验证和必要的缺口修复：

- DDD 五层模块结构。
- WebFlux 函数式路由和 Handler。
- JWT Access Token、Refresh Token 和 Spring Security。
- RBAC、菜单权限、按钮权限和部分数据权限。
- MyBatis-Plus、Flyway、MySQL 和动态数据源。
- Caffeine、Redis、Redisson 和多级缓存。
- RocketMQ、消费幂等、Outbox 和死信处理基础能力。
- Sentinel、Resilience4j、限流、熔断和超时控制。
- 操作审计、登录日志、接口日志和 TraceId。
- 文件存储抽象、Excel 导入导出和 SSE。
- Prometheus、Grafana、健康检查和基础部署配置。
- 后端 DDD 代码生成器及部分 Vue3 文件模板。
- Basic、Standard、Enterprise Profile 和 License FeatureGate。

### 3.2 本方案重点增强范围

本方案重点关注六类能力：

1. 通用业务基础能力。
2. 企业系统管理和组织权限能力。
3. 多租户与数据隔离能力。
4. 业务流程、状态和任务能力。
5. 业务模块开发和代码生成能力。
6. 业务交付、运行维护和验收能力。

### 3.3 本方案暂不默认纳入的内容

以下内容不作为第一阶段默认开发项，除非后续确认需要：

- 面向某个具体行业的完整业务系统。
- 财务、供应链、生产制造等深度行业模型。
- 自研工作流引擎底层运行时。
- 大规模 BI 数仓和实时数仓。
- 完整低代码平台。
- 面向所有国产数据库的一次性全面适配。

## 4. 总体目标

增强后，客户应能够完成以下标准流程：

1. 选择版本并初始化一个新项目。
2. 配置数据库、Redis、对象存储和可选消息服务。
3. 创建租户、部门、用户、角色和菜单权限。
4. 使用代码生成器创建一个包含实体、仓储、服务、Handler、路由、迁移和前端页面的业务模块。
5. 为业务模块配置列表、详情、创建、编辑、删除、批量操作、导入导出和审计。
6. 对关键业务操作配置幂等、状态校验、数据权限、租户隔离和操作日志。
7. 通过 Docker Compose 或 Kubernetes 部署。
8. 使用监控、审计、备份恢复和验收脚本完成交付。

目标不是把所有业务预先做成固定模块，而是提供稳定、可组合、可扩展的业务能力积木。

## 5. 需求优先级定义

| 等级 | 定义 | 处理原则 |
|---|---|---|
| P0 | 影响通用业务可用性、数据安全或商业交付 | 首发版本必须完成 |
| P1 | 显著提升开发效率和企业项目复用率 | 首发后优先完成 |
| P2 | 行业差异化或规模化能力 | 根据客户项目和销售反馈实施 |

## 6. P0 通用业务能力增强需求

### BIZ-001 统一业务模块基类与约定

#### 目标

为客户业务模块提供统一的领域实体、分页查询、审计字段、逻辑删除、租户字段、版本字段和异常处理约定，减少不同模块之间的实现差异。

#### 需求内容

- 统一业务实体基础字段：`id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`deleted`、`version`、`tenant_id`。
- 明确哪些字段由系统自动填充，业务代码不得自行覆盖。
- 统一创建、更新、删除、恢复和批量删除语义。
- 统一分页参数校验，限制最大页大小。
- 统一排序字段白名单，禁止直接拼接用户输入。
- 统一领域异常、参数异常、权限异常和并发冲突异常映射。
- 统一业务模块包结构和命名规范。
- 为生成器和人工开发提供同一套约定。

#### 业务规则

- 默认启用逻辑删除，物理删除只能由明确的基础设施任务执行。
- 更新必须携带版本号或使用明确的并发策略。
- 查询必须显式声明租户和数据权限上下文。
- 所有分页查询必须限制最大页大小。
- 所有可排序字段必须来自服务端允许列表。

#### 验收标准

- 新生成模块包含完整基础字段和统一 Mapper 行为。
- 未授权租户无法查询或修改其他租户数据。
- 并发更新冲突能返回稳定错误码。
- 非法排序字段不会进入 SQL。
- 生成模块可以通过编译、迁移和基础接口测试。

### BIZ-002 统一查询、分页、排序和筛选能力

#### 目标

解决各业务模块重复实现分页和动态条件的问题，形成可复用的安全查询能力。

#### 需求内容

- 支持关键字、精确匹配、范围、时间区间、枚举、多选和空值条件。
- 支持嵌套条件组合，至少覆盖 AND、OR 和 NOT 的有限表达。
- 支持服务端排序白名单和默认排序。
- 支持分页和游标分页两种模式。
- 支持查询条件 DTO 校验。
- 支持导出查询条件复用。
- 支持查询条件与数据权限、租户条件自动合并。

#### 业务规则

- 查询条件不得直接转换为任意 SQL 片段。
- 默认查询只返回当前租户和当前用户有权访问的数据。
- 导出必须复用列表查询条件，但必须额外限制导出条数或采用异步导出。
- 大数据量场景必须使用游标或异步任务，不允许无限分页。

#### 验收标准

- 同一组条件在列表和导出中得到一致的数据集合。
- 租户条件和数据权限条件无法被前端参数覆盖。
- 分页、排序、范围查询在 MySQL 实际环境通过测试。
- 超过最大页大小或最大导出量时返回明确错误码。

### BIZ-003 统一状态机和业务状态流转

#### 目标

为订单、申请、审批、任务、发布、工单等业务提供统一状态流转约束，避免状态字段被任意修改。

#### 需求内容

- 提供状态定义、允许迁移、迁移条件和迁移动作模型。
- 支持状态迁移前校验、迁移后事件和操作审计。
- 支持幂等状态迁移。
- 支持并发更新保护。
- 支持状态迁移历史查询。
- 支持状态变更原因和业务备注。
- 支持禁止跳转、回退和终态保护。

#### 业务规则

- 业务方只能调用状态迁移操作，不能直接修改状态字段。
- 终态默认不可修改，特殊回退必须具有独立权限。
- 重复提交同一状态迁移必须返回幂等结果，不得重复执行副作用。
- 状态迁移和迁移日志必须在同一业务事务边界内完成。

#### 验收标准

- 非法状态迁移被拒绝并返回明确错误码。
- 合法迁移只执行一次。
- 状态历史包含操作人、时间、原状态、新状态、原因和 TraceId。
- 并发状态更新至少有一方得到冲突结果。

### BIZ-004 批量操作和异步任务能力

#### 目标

支持企业系统常见的批量启用、停用、删除、导入、导出、通知和数据处理任务。

#### 需求内容

- 统一批量请求结构和批量结果结构。
- 支持全成功、部分成功和全部失败三种结果。
- 支持单条失败原因和可重试标识。
- 支持批量操作权限校验和数据权限校验。
- 大批量操作转为异步任务。
- 提供任务进度、状态、失败记录和结果下载。
- 支持任务取消、重试和过期清理。
- 批量操作写入审计日志。

#### 业务规则

- 批量接口必须限制单次最大记录数。
- 不允许因为部分数据无权限而绕过权限检查。
- 异步任务必须记录提交人、租户、参数摘要和执行结果。
- 任务重试必须具备幂等策略。
- 任务参数不得在日志中记录密码、Token、密钥等敏感数据。

#### 验收标准

- 批量操作返回逐条结果或可下载结果文件。
- 大批量任务不会阻塞 WebFlux 请求线程。
- 任务状态在重启后不会出现无法解释的中间状态。
- 重复执行同一任务不会造成重复业务副作用。

### BIZ-005 统一导入导出业务能力

#### 目标

将现有 Excel 能力提升为可复用的企业数据交换组件，而不是每个业务模块单独实现。

#### 需求内容

- 支持模板下载、文件上传、格式校验、业务校验和错误行回传。
- 支持预览校验后再正式导入。
- 支持同步小文件导入和异步大文件导入。
- 支持导出任务和结果文件过期清理。
- 支持导入批次号、导入人、导入时间和结果统计。
- 支持字段脱敏和导出列权限。
- 支持导入失败记录下载。

#### 业务规则

- 上传文件必须校验大小、扩展名、MIME 类型和文件内容。
- 导入数据必须经过租户、数据权限和业务唯一性校验。
- 导出字段必须根据角色权限过滤。
- 临时文件必须设置过期时间并清理。

#### 验收标准

- 非法文件不会进入业务处理流程。
- 导入失败时能定位到行号、字段和错误原因。
- 导出结果不包含无权限字段。
- 大文件导入导出采用异步任务且可查询进度。

## 7. P0 企业系统管理增强需求

### SYS-001 组织架构和用户生命周期

#### 目标

形成可支持企业组织管理的用户、部门、岗位和状态生命周期。

#### 需求内容

- 用户、部门、岗位、职级和组织树模型。
- 用户状态：待激活、正常、锁定、停用、离职。
- 用户入职、转岗、调部门、离职和重新激活。
- 支持一个用户多个岗位和多个部门关系。
- 支持部门负责人和岗位负责人。
- 支持批量导入组织架构。
- 支持密码策略、初始密码和首次登录强制改密。
- 支持用户强退、会话失效和登录设备管理。

#### 业务规则

- 停用或离职用户不能获得新 Token。
- 用户离职后历史数据的创建人和操作人信息必须保留。
- 删除部门前必须检查子部门、用户和业务数据引用。
- 组织调整不得自动篡改历史审计记录。

#### 验收标准

- 用户生命周期操作均有审计记录。
- 组织树调整后数据权限按规则生效。
- 停用用户的已有会话能按配置立即或延迟失效。
- 用户导入错误可定位到具体行和字段。

### SYS-002 角色、菜单、按钮和数据权限闭环

#### 目标

建立前后端一致的权限模型，覆盖页面访问、按钮操作、接口访问和数据范围。

#### 需求内容

- 菜单权限、按钮权限、接口权限和数据范围权限统一模型。
- 数据范围支持本人、本部门、本部门及下级、指定部门、指定租户和全部数据。
- 支持角色继承或角色组合，至少明确不支持时的边界。
- 支持权限变更后的缓存刷新和会话生效策略。
- 支持权限预览和用户有效权限查询。
- 支持前端动态菜单与后端接口鉴权一致性检查。
- 支持权限编码唯一性校验。

#### 业务规则

- 前端隐藏按钮不能替代后端鉴权。
- 数据范围由服务端根据用户上下文生成，前端不能直接传入最终 SQL 条件。
- 超级管理员能力必须有明确配置，不能通过普通角色名称硬编码绕过。
- 权限变更必须可追溯。

#### 验收标准

- 页面、按钮、接口和数据范围四层权限均有测试。
- 用户无权限时返回统一错误码和 TraceId。
- 权限变更后缓存和 Token 行为符合文档约定。
- 任意业务模块可通过统一注解或服务完成权限接入。

### SYS-003 字典、枚举和参数配置增强

#### 目标

让业务模块可以安全使用可配置字典和运行时参数，避免把业务选项硬编码到代码中。

#### 需求内容

- 字典类型、字典项、排序、状态和扩展属性。
- 字典项多语言名称。
- 参数配置类型：字符串、整数、小数、布尔、JSON、密文。
- 参数配置默认值、有效期和变更审计。
- 参数缓存、主动刷新和灰度生效。
- 参数值格式校验。
- 敏感参数只允许写入和脱敏展示，不允许明文查询。

#### 验收标准

- 字典缓存更新后业务读取行为可预期。
- 非法参数值无法保存。
- 敏感参数在响应、日志和审计中均不可还原。
- 字典和参数变更有完整操作记录。

### SYS-004 定时任务和执行记录增强

#### 目标

将已有定时任务能力规范化，支持企业客户管理任务、重试和执行审计。

#### 需求内容

- 任务定义、Cron 校验、启停、手动触发和执行日志。
- 任务并发策略：禁止并发、允许并发、按租户串行。
- 超时、重试、退避和最大执行次数。
- 执行结果摘要和失败原因。
- 任务权限和人工触发审计。
- 任务分布式执行策略和单实例锁策略。
- 任务执行上下文中的租户和 TraceId 传递。

#### 业务规则

- 用户手动触发不能绕过任务权限。
- 任务失败不能无限重试。
- 任务日志不得记录完整敏感参数。
- 多实例部署时必须明确任务是否允许重复执行。

#### 验收标准

- Cron 非法表达式无法保存。
- 任务按配置执行并产生可查询记录。
- 超时、失败和重试状态可区分。
- 多实例部署不会产生未预期的重复执行。

## 8. P0 多租户与数据隔离增强需求

### TENANT-001 租户模型和租户生命周期

#### 目标

形成适用于 SaaS 和私有化多组织场景的租户基础模型。

#### 需求内容

- 租户基础信息、编码、状态、套餐、有效期和管理员。
- 租户创建、启用、停用、冻结、注销和归档。
- 租户配额：用户数、存储量、并发数、API 调用量和功能集。
- 租户级参数、字典、菜单和数据范围。
- 租户管理员和平台管理员的权限边界。
- 租户上下文解析、校验和全链路传递。

#### 业务规则

- 停用租户不得创建新业务数据。
- 租户过期后的访问策略必须可配置，至少支持拒绝写入和全部拒绝两种模式。
- 平台管理员访问租户数据必须产生特殊审计记录。
- 租户编码必须全局唯一。

#### 验收标准

- 租户状态变化能影响登录和业务操作。
- 同一用户在不同租户中的角色和数据范围隔离。
- 租户配额超限返回明确业务错误。
- 跨租户访问测试全部失败并产生审计记录。

### TENANT-002 租户隔离策略统一化

#### 目标

避免不同业务模块以不同方式实现租户隔离，形成可检查、可测试的统一规范。

#### 需求内容

- 统一租户字段名称和类型。
- 统一租户上下文来源：Token、请求头、平台切换和任务上下文。
- 统一 SQL 条件注入或仓储层过滤机制。
- 对不需要租户字段的系统表建立白名单。
- 对跨租户统计、平台报表和数据迁移建立显式权限接口。
- 增加架构测试，检查业务表和 Mapper 是否遵守租户规范。

#### 业务规则

- 普通业务查询默认必须带租户条件。
- 请求头中的租户标识不能覆盖 Token 中的可用租户范围。
- 异步消息和定时任务必须携带租户上下文。
- 跨租户操作只能通过平台级服务完成。

#### 验收标准

- 新增生成模块默认具备租户隔离。
- Mapper、Repository 和批量操作均有租户隔离测试。
- 消息消费和异步任务不会丢失租户上下文。
- 架构测试能阻止不符合约定的业务模块进入发布流程。

## 9. P1 业务开发效率增强需求

### DEV-001 一键初始化和项目模板化

#### 目标

让客户从脚手架仓库到可运行项目的过程从手工改名变成可重复命令。

#### 需求内容

- 项目名称、组织名、包名和服务名替换。
- Basic、Standard、Enterprise 版本选择。
- 数据库、Redis、对象存储、MQ 开关选择。
- 开发、测试、生产环境配置生成。
- 初始管理员和租户初始化。
- Flyway 初始迁移选择。
- Docker Compose 文件生成。
- License 配置和版本标识生成。
- 初始化结果校验和失败回滚。

#### 验收标准

- 全新目录中执行一次命令即可生成可构建项目。
- 生成项目中不存在原项目包名和品牌残留。
- 生成项目可以执行构建、启动和初始化迁移。
- 参数错误时不生成半成品，或能明确清理并恢复。

### DEV-002 业务代码生成器增强

#### 目标

将当前按 JSON 生成代码的方式提升为可供企业项目长期使用的业务模块生成工具。

#### 需求内容

- 支持从 MySQL 表结构读取定义。
- 支持 JSON、数据库和交互式命令行三种输入方式。
- 支持字段类型、长度、精度、默认值、必填、枚举和字典配置。
- 支持列表、详情、创建、更新、删除、批量操作和导入导出生成选项。
- 支持租户、审计、乐观锁和逻辑删除开关。
- 支持权限编码自动生成。
- 支持菜单、按钮和 Flyway 初始化数据生成。
- 支持 Vue3 API、列表页、表单页、详情页和路由片段生成。
- 支持生成后自动执行格式化和编译检查。
- 支持覆盖保护、差异预览和重复生成策略。

#### 验收标准

- 生成后端代码、迁移文件和前端页面可以在样例工程中真实编译。
- 重复生成不会无提示覆盖人工修改。
- 字段校验、数据库类型和 TypeScript 类型映射一致。
- 生成的权限编码、菜单数据和接口路径一致。
- 至少覆盖用户、商品、订单三类典型表结构。

### DEV-003 业务接口契约和版本管理

#### 目标

降低前后端联调成本，避免业务接口升级造成客户项目不可控。

#### 需求内容

- 所有业务接口必须生成 OpenAPI 描述。
- 统一请求、响应、分页、错误码和 TraceId 结构。
- 支持 API 版本和兼容策略。
- 明确字段新增、字段废弃、枚举新增和错误码变更规则。
- 支持生成 TypeScript 类型和客户端调用代码。
- 支持契约测试，检查路由、权限、响应和文档一致性。

#### 验收标准

- 新增业务接口未声明 OpenAPI 时构建或测试失败。
- 前端类型可以由后端契约生成或校验。
- 版本升级文档包含兼容性说明。
- 破坏性变更有明确版本号和迁移说明。

## 10. P1 企业业务组件增强需求

### COMP-001 通知中心

#### 目标

提供站内信、邮件、短信和企业 IM 的统一通知业务抽象。

#### 需求内容

- 通知模板、变量、渠道、优先级和租户范围。
- 站内信读、未读、批量已读和过期。
- 邮件、短信、企业微信或钉钉适配 SPI。
- 发送记录、失败原因、重试和死信。
- 用户免打扰和通知偏好。
- 敏感信息脱敏和模板权限控制。

#### 验收标准

- 业务模块通过统一服务发送通知，不直接依赖具体厂商 SDK。
- 发送失败可查询并按策略重试。
- 不同租户的模板和发送记录隔离。
- 未配置外部渠道时基础站内信仍可用。

### COMP-002 文件与附件中心

#### 目标

将现有存储抽象提升为面向业务的附件管理能力。

#### 需求内容

- 文件元数据、业务关联、租户、上传人和生命周期。
- 本地、MinIO、S3 和国产对象存储适配。
- 分片上传、断点续传和大文件异步处理。
- 访问权限、临时下载地址和防盗链。
- 病毒或内容安全扫描扩展点。
- 文件版本、删除、恢复和过期清理。
- 附件与业务单据的关联和解绑。

#### 验收标准

- 文件访问必须经过业务权限检查。
- 直接猜测文件地址不能访问受保护文件。
- 租户之间不能读取附件元数据和内容。
- 文件生命周期任务可重复执行且具备幂等性。

### COMP-003 操作记录和业务审计增强

#### 目标

让系统审计不仅记录“谁调用了接口”，还能够解释“业务对象发生了什么变化”。

#### 需求内容

- 业务对象类型、对象 ID、操作类型和业务单号。
- 变更前后字段差异。
- 脱敏规则和敏感字段白名单。
- 批量操作的父子审计记录。
- 状态迁移、导入导出、权限变更和租户切换审计。
- 审计检索、导出和归档策略。
- 审计记录防篡改和访问权限。

#### 验收标准

- 关键业务变更可以定位到用户、租户、时间、来源和 TraceId。
- 密码、Token、密钥和隐私字段不会进入审计明文。
- 审计日志查询有数据权限和租户隔离。
- 审计记录可关联到业务对象和状态历史。

### COMP-004 业务唯一性和幂等中心

#### 目标

统一处理订单号、业务编码、幂等键和重复提交，避免每个模块自行实现。

#### 需求内容

- 业务编码生成规则和租户范围。
- 唯一性校验服务。
- 请求幂等键、业务幂等键和消息幂等键区分。
- 幂等记录状态：处理中、成功、失败、过期。
- 幂等响应缓存和重试策略。
- 数据库唯一索引与应用校验协同。

#### 验收标准

- 并发请求不能生成重复业务编码。
- 同一幂等键重复请求不会重复执行副作用。
- 失败请求是否允许重试有明确配置。
- 幂等记录在 Redis 不可用时有明确降级行为。

## 11. P1 业务流程和审批能力

### FLOW-001 轻量业务流程编排

#### 目标

在不立即建设完整工作流引擎的前提下，为常见申请、审核、驳回和撤回场景提供标准业务流程模型。

#### 需求内容

- 流程定义、版本和启停。
- 节点类型：发起、审批、抄送、条件、结束。
- 审批人来源：指定用户、角色、部门负责人、发起人上级。
- 审批动作：同意、驳回、转交、加签、撤回。
- 流程实例、待办、已办和操作记录。
- 流程与业务单据关联。
- 超时提醒和自动处理扩展点。

#### 业务规则

- 流程定义发布后不能直接修改已运行实例的历史节点。
- 审批人变更不应篡改已完成记录。
- 审批动作必须校验当前待办归属和版本。
- 流程实例必须携带租户和业务对象上下文。

#### 验收标准

- 典型请假、采购申请或费用申请能够跑通。
- 审批、驳回、撤回和转交的权限边界明确。
- 流程记录可追溯，业务单据状态与流程状态一致。
- 多租户之间流程定义、实例和待办完全隔离。

## 13. 接口和数据模型统一要求

### 13.1 统一响应

业务接口统一返回以下结构：

```json
{
  "code": 0,
  "msg": "成功",
  "data": {},
  "traceId": "trace-id"
}
```

具体要求：

- 成功、业务失败、参数失败、权限失败和系统失败使用统一错误码体系。
- 分页响应必须包含总数、页码、页大小和数据项。
- 异步任务响应必须返回任务 ID 和查询地址。
- 错误响应不得泄露 SQL、堆栈、密钥和内部地址。

### 13.2 统一错误码

需要建立按领域划分的错误码段，例如：

- `1xxx`：认证和会话。
- `2xxx`：权限和数据范围。
- `3xxx`：租户和组织。
- `4xxx`：业务校验和状态冲突。
- `5xxx`：文件、导入和导出。
- `6xxx`：任务和消息。
- `9xxx`：系统和依赖服务。

要求所有旧错误码和新错误码在实施前形成映射表，不允许同一业务含义存在多个未说明的编码。

### 13.3 统一审计字段

所有可持久化业务表原则上包含：

- 主键。
- 租户 ID。
- 创建时间和创建人。
- 更新时间和更新人。
- 逻辑删除标识。
- 乐观锁版本。
- 必要的业务状态。

不适用字段必须在表设计说明中明确原因。

## 14. 业务代码质量要求

### 14.1 分层要求

- Domain 只包含领域模型和仓储接口，不依赖 Web、数据库实现和具体消息客户端。
- Application 负责用例编排、事务边界和权限上下文协调。
- Infrastructure 负责数据库、缓存、消息、文件和外部服务适配。
- Interfaces 负责协议转换、参数校验、认证授权和路由。
- Handler 不直接编写复杂 SQL、跨模块事务或外部 SDK 调用。

### 14.2 响应式要求

- WebFlux 请求链路不得执行未调度的阻塞 I/O。
- MyBatis、文件和外部阻塞客户端必须使用明确的调度策略。
- SSE、异步任务和消息消费必须具备取消、超时和背压策略。
- 不允许通过 `block()` 规避响应式链路设计。

### 14.3 安全要求

- 所有业务接口默认需要认证，公开接口必须有白名单说明。
- 所有写接口必须评估幂等和重放风险。
- 所有查询必须评估租户、数据权限和敏感字段。
- 所有文件接口必须评估路径穿越、类型伪造和越权下载。
- 所有导入接口必须评估公式注入、超大文件和恶意内容。
- 所有日志和审计必须经过脱敏。

### 14.4 测试要求

每个新增通用组件或业务模块至少包含：

- 正常业务路径。
- 参数校验失败。
- 未认证和无权限。
- 租户越权。
- 数据范围越权。
- 重复提交或并发冲突。
- 外部依赖失败。
- 超时、重试或降级。
- 审计记录。
- OpenAPI 和路由契约。

## 17. 统一验收方案

### 17.1 功能验收

- 创建租户、部门、用户、角色和菜单。
- 登录、刷新 Token、强退和停用用户。
- 创建一个生成业务模块并完成迁移。
- 完成列表、详情、创建、编辑、删除和批量操作。
- 完成导入、错误行下载和导出。
- 完成状态流转、驳回、重复提交和并发冲突。
- 完成审计查询和业务变更追踪。
- 完成定时任务和异步任务查询。

### 17.2 安全验收

- 未认证请求无法访问受保护接口。
- 无按钮权限不能执行对应操作。
- 无数据范围权限不能读取或修改数据。
- 不同租户数据完全隔离。
- 文件不能越权下载。
- 导入文件不能造成公式注入和路径穿越。
- 敏感数据不出现在响应、日志和审计明文中。

### 17.3 工程验收

- 生成代码可以编译。
- Flyway 迁移可以执行和回滚到支持的版本。
- OpenAPI、路由、权限和前端调用一致。
- 单元测试、集成测试和契约测试通过。
- 真实 MySQL、Redis 和可选 MQ 环境验证通过。
- Docker Compose 最小环境可启动。
- Kubernetes 探针、配置和滚动升级可验证。

### 17.4 商业交付验收

- Basic、Standard、Enterprise 的功能边界和依赖树一致。
- License 无效时商业功能按规则拒绝。
- 文档、代码、构建产物和销售清单一致。
- 生产环境不能使用默认密码和默认密钥直接启动。
- 备份、恢复、升级和回滚过程有可复现记录。
- 所有对外承诺都有测试或演示证据。

## 18. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 业务规范过多导致脚手架过重 | 客户学习成本上升 | Basic 保持轻量，企业能力按 Profile 和模块启用 |
| 租户和数据权限实现不一致 | 严重数据越权 | 统一上下文、架构测试、跨租户集成测试 |
| 生成器覆盖人工代码 | 客户项目代码丢失 | 差异预览、覆盖保护和生成目录隔离 |
| 异步任务重复执行 | 重复扣款或重复通知 | 任务幂等键、业务唯一索引和执行状态机 |
| 外部依赖不可用 | 业务请求失败 | 超时、重试、熔断、降级和明确错误码 |
| 工作流过早自研 | 研发和维护成本过高 | 优先采用成熟引擎适配，保留 SPI |
| 商业版本宣传与产物不一致 | 客户投诉和授权风险 | 三档构建、依赖、启动和功能矩阵自动验收 |
| 文档与代码漂移 | 交付不可验收 | 每次发布同步更新版本基线和证据链接 |

## 19. 方案确认项

执行前需要确认以下事项：

1. 是否同意以“通用业务能力积木 + 企业管理基础能力 + 代码生成器”为主要增强方向。
2. 是否将多租户、数据权限、状态机、批量任务和统一业务基类列为 P0。
3. 是否将完整独立 Vue3 管理后台纳入 Standard 和 Enterprise 正式交付物。
4. 是否采用 Basic、Standard、Enterprise 三档能力边界。
5. 是否优先支持单体模块化和私有化部署，而不是先建设微服务拆分能力。
6. 是否优先接入成熟工作流引擎，而不是第一阶段自研工作流底层。
7. 是否将国产数据库适配安排在企业客户签约后按项目实施。
8. 是否接受阶段一先做基线验证、契约补齐和现有能力整合，再进行新增业务代码开发。

## 20. 确认后的执行顺序

方案确认后，按以下顺序进入执行：

1. 锁定版本和当前代码事实基线。
2. 对现有业务能力进行接口、数据模型和权限盘点。
3. 建立统一错误码、基础字段、租户上下文和业务模块规范。
4. 为 P0 需求编写测试和验收用例。
5. 实现通用业务组件和基础服务。
6. 接入示例模块，形成可运行能力地图。
7. 接入代码生成器和前端生成模板。
8. 完成真实数据库、缓存、消息和部署环境验证。
9. 更新商业版本矩阵、交付文档和销售材料。
10. 通过最终验收后再形成正式发行包。

在用户确认本方案前，不执行上述代码、配置、测试或文档改造。
