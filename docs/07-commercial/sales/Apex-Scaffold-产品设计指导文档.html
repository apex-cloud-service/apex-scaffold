1.2 三条设计总原则

  • 能力复用优先：本平台的认证、权限、审计、通知、文件能力均为共享底座，新功能设计时先问「底座能不能直接挂」，不要为单模块重新发明账号体系或消息通道。
  • 权限先行：任何页面的第一张草稿应是「谁看得见、谁点得动、数据范围多大」（功能权限 + 数据权限 + 租户三问），再画布局。
  • 约定即规范：§5 的约定全部由代码强制执行（网关、拦截器、门禁），产品设计若与其冲突，实现成本会急剧上升——这些是红线不是建议。

02产品全局认知

2.1 一句话定位

Apex Scaffold 是一套企业级 Java 后端平台底座：以「网关 + 微服务」形态交付认证、权限、系统管理、工作流、办公集成、文件、任务调度等公共能力，业务方在其上快速搭建企业内部系统或行业 SaaS。

3.2 角色画像与设计要点

角色核心诉求主要功能入口设计要点
超级管理员
ADMIN / SUPER_ADMIN		 掌控全局：账号、权限、系统配置、安全治理 系统管理全部目录 + 监控中心 + 认证配置 关键操作是双保险（管理角色硬校验 + 权限码），高危操作（改权限、踢人、删菜单）设计二次确认 + 审计留痕提示；界面默认全量可见，但应支持按模块折叠。
系统管理员/运维 系统健康、日志排查、任务与数据源运维 监控中心、日志四件套、任务调度、数据源管理 大屏五视图（总览/系统/中间件/治理/业务）适合做导航首页；日志检索页面要突出 traceId 关联跳转；权限码 system:monitor:view 一码控五视图，如需细分要提需求拆码。
租户管理员
（当前无此界面）		 管本租户的用户、套餐配额、到期情况 待设计（租户模型与配额字段已备） 租户身份来自 JWT、不可伪造切换——UI 上若做「租户切换器」仅是视觉呈现，后端无感知；配额四项（套餐/到期/用户数/存储）适合做仪表卡。
部门主管 看本部门（及下级）的人员与业务数据 后台用户列表、各类业务列表 数据范围由角色的 data_scope 决定（本部门/本部门及以下等五档），界面上不需要也不应提供范围切换；列表页应明确展示「当前数据范围」提示，避免误解为数据缺失。
普通业务用户
ROLE_USER		 个人事务：待办、消息、文件、个人信息 工作台（/dashboard）、我的待办、收件箱、个人中心 所有接口走 /api/v1/**；个人中心含自助注销（验证码二次确认）属合规要求不可省略；首页信息密度要低，聚焦待办 + 未读消息 + 快捷入口。
审批人 高效处理待办、了解流程上下文 我的待办、审批详情、历史 四个干预动作（通过/回退/转办/委派）语义不同，交互上要分开呈现且不可合并；超时升级（转办管理员）产生的任务要有特殊标识。
第三方开发者 接入 OAuth2/OIDC 拿到用户授权 开放端点 + 管理侧客户端管理 面向开发者的文档页需要 OIDC 发现地址、JWKS、端点清单；客户端密钥有自动轮换调度，开发者文档要写明轮换后的处理。
办公平台用户 在钉钉/飞书/企微里用核心功能，免双系统切换 办公扫码登录、平台内消息/审批卡片 账号绑定有审核流（binding review），设计要包含「绑定申请→审核→生效」状态可见；消息外发失败有重发/撤回，需要给状态反馈。

04功能模块设计指引

每个模块给出四件事：现有能力（浓缩）、建议信息架构、设计要点、风险与依赖。详细接口清单查基线文档 §5。

4.1 认证与账号中心

维度内容
现有能力账密登录（5 次失败锁 30 分）、ACCESS 2h/REFRESH 7d 双令牌（刷新一次性轮换）、MFA（TOTP/短信/邮箱+备份码）、会话管理/强踢、OAuth2/OIDC、SSO、IP 黑白名单、密码策略可配、登录审计。
建议信息架构登录页（账密 / 验证码 / SSO 入口 / MFA 步进式）→ 个人安全中心（改密、MFA 管理、设备信任、登录记录、账号注销）→ 管理侧：认证配置（JWT/会话/安全策略）、在线会话、登录日志。
设计要点① MFA 绑定走「setup→verify→生效」三步向导，备份码展示一次性且要求确认已保存；② 刷新令牌被重复使用会整族撤销，前端需对 401 做统一「回到登录」处理；③ 图形验证码一次性，失败后要刷新。
风险与依赖密码找回无后端端点——PRD 需与后端排期；认证中心错误消息暂为硬编码中文（i18n 机会点）。

4.2 用户与组织管理

维度内容
现有能力用户（增删改查/启停/角色替换/会话撤销/Excel 导出）、角色（CRUD+数据范围）、权限码、菜单树（目录/页面/按钮三级）、部门树（ancestors 链）、字典（类型+数据）、参数配置。
建议信息架构组织管理（部门树 + 成员列表双栏）→ 权限管理（角色列表 → 角色详情页三个 Tab：功能权限 / 数据权限 / 成员）→ 系统配置（字典 / 参数）。
设计要点① 角色详情页是本模块核心：数据权限五档选择器（全部/本部门/本部门及以下/仅本人/自定义）+ 自定义时的部门树多选，务必做「保存前预览影响范围」；② 按钮级权限 = 菜单类型 2，前端按钮显隐按权限码渲染；③ 用户状态变更与删除要联动提示「将撤销其在线会话」。
风险与依赖权限码即种子数据，新增页面需同步提权限码种子与菜单种子（有迁移脚本流程）；菜单种子历史上有 id 冲突（V33/V38），前端按最终形态设计。

4.3 工作流与审批

维度内容
现有能力按编码发起实例、我的待办、通过/回退/转办/委派、挂起/恢复、实例列表与统计趋势、超时升级扫描（本地或 XXL 接管）。
建议信息架构用户侧：发起入口（流程中心）→ 我的待办 → 我发起的 → 详情页（轨迹时间线 + 操作区）。管理侧：流程定义管理（待建）→ 实例监控 → 统计报表。
设计要点① 流程定义管理是本模块最大空白，建议蓝图见 §6 机会点 2；② 详情页轨迹需要展示 审批记录 + 回退/转办/委派痕迹 + 超时升级标识；③ 统计趋势适合管理驾驶舱首页。
风险与依赖定义 CRUD/设计器端点尚未实现，PRD 需与后端共同评审模型；多实例部署时超时扫描需单机路由，属部署约束。

4.4 消息与通知（建议整合为统一消息中心）

维度内容
现有能力自研站内信（HTTP 收件箱 + WS 实时提醒，30s 一次性握手票据，断线 HTTP 补偿）、SSE 通知流、消息模板管理、办公平台消息外发（状态/重发/撤回）。
建议信息架构统一收件箱（全部 / 系统通知 / 审批 / 办公平台，Tab 化）+ 未读角标（顶栏全局）+ 消息详情（按类型差异化渲染）+ 模板管理（管理侧）。
设计要点① 当前站内信（office）与系统通知（system SSE/收件箱）是两条链路，建议按左侧目标架构整合呈现、逐步合并存储；② WS 断线重连后必须调 HTTP 收件箱补拉，前端要做「连接状态」降级提示；③ 实时推送仅在单实例内有连接态，横向扩展需粘性路由——SLA 文案要如实。
风险与依赖站内信连接注册表为单实例内存态；多实例广播依赖 RocketMQ（企业能力域）。

4.5 文件与文档中心

维度内容
现有能力直传、分片上传（init/upload/merge/status/cleanup）、授权流式下载、预览、预签名 URL（云存储 1s~7 天）、孤儿清理、文档与图表台账、五后端存储（Local/MinIO/OSS/TOS/七牛）。
建议信息架构我的文件（列表 + 上传器组件）→ 分享（待建）→ 文档台账（管理侧）→ 存储配置（运维侧）。
设计要点① 上传器组件按大小自动切换直传/分片，分片展示进度与失败重试（cleanup 接口兜底）；② 预签名有效期要作为可配置项透出到产品设置；③ 删除后涉及孤儿文件对账，交互上提示「异步清理」。
风险与依赖分享链接无端点（见 §6 机会点 5）；Local 后端无无认证预签名，外链功能依赖云存储。

4.6 监控与运维中心

维度内容
现有能力大屏五视图（overview/system/middleware/governance/business）、登录/操作审计/API 调用/运行时/业务日志、在线用户、统一搜索（可配 Meilisearch）、任务调度（CRUD/执行/日志）、数据源管理（多源/指标/主从）。
建议信息架构监控首页（五视图 Tab 或卡片宫格）→ 日志中心（四类日志统一检索壳 + 类型切换）→ 任务中心 → 数据源管理 → 在线用户。
设计要点① 日志中心统一壳设计价值最高：一个检索页 + 类型维度切换，共享时间范围/traceId 过滤器；② 在线用户页强踢操作要二次确认且写入操作审计；③ 大屏指标来自 Prometheus，页面文案避免承诺实时性（采集有周期）。
风险与依赖Grafana 已有 96+14+11 面板，管理后台的自研大屏与其定位要区分（自研 = 业务向摘要，Grafana = 技术向深查）。

4.7 平台配置与扩展

维度内容
现有能力SSO 提供商管理（CRUD/测试/元数据/会话/审计）、OAuth2 客户端管理（密钥自动轮换）、Keycloak 对接（条件装配）、代码生成器（数据源→选表→配置→生成）、数据库配置与多数据源管理、办公应用与绑定审核。
建议信息架构集成中心（SSO / OAuth2 / 办公平台 三个子页）→ 开发者工具（代码生成器向导）→ 系统配置（数据库/数据源）。
设计要点① 代码生成器建议做成四步向导（连数据源 → 选表 → 配置选项 → 预览生成），历史记录可回溯；② 办公应用登记（按平台填凭据）建议做成向导并内置「连接测试」；③ 绑定审核列表是安全敏感页，操作留痕要显著。
风险与依赖Keycloak/OIDC 相关页面仅在 keycloak.enabled=true 时出现，前端要做条件菜单。

05全局设计规范（红线与约定）

以下条目均由代码或网关强制执行，产品设计必须遵守；每条附「对设计的含义」。

5.1 信息架构与路由约定

平台约定对设计的含义
接口分三类前缀：/api/v1（用户侧）、/admin-api/v1（管理侧）、/auth/v1（认证协议）前端路由与菜单按「用户门户 / 管理后台」两大区组织；同一功能不要横跨两类前缀混排。
菜单三级模型：目录(0) / 页面(1) / 按钮(2)，按钮即操作权限原型阶段的每个按钮都应标注权限码；没有权限码的按钮等于人人可用。
管理接口双重校验：管理角色硬校验 + Handler 权限码仅给用户分配「管理角色」不够，必须在角色上勾选具体权限码；权限配置界面按此双维度设计。
统一响应 Result<T>：业务成功码为 0（≠HTTP 200），含 traceId全局错误提示组件按 code 分支；所有错误弹层展示可复制的 traceId，便于排障。

5.2 权限与数据设计红线

六条红线（违反即返工） ① 数据权限五档由角色决定，不得设计「用户自选数据范围」；
② 租户身份来自 JWT，不得设计「请求头切换租户」的交互（如需多租户视图，走账号体系设计）；
③ 刷新令牌一次性，任何页面不得缓存/复用旧令牌；401 统一回登录；
④ 审计与日志是平台行为（操作审计/登录日志/API 调用日志），产品上不得设计「关闭审计」开关；
⑤ 高危操作（强踢、删菜单、改权限、解绑、撤会话）必须二次确认并提示将留痕；
⑥ 身份相关请求头（X-User-Id 等）网关强制剥离，前端不得依赖任何本地身份伪装。

5.3 实时与异步交互规范

场景平台行为交互设计要求
站内信实时提醒WS + 20s 心跳、60s 失活；断线后 HTTP 补拉显示连接状态；重连后合并去重补拉消息；票据 30s 一次性由前端静默获取。
系统通知SSE 流（/notifications/stream）SSE 断开自动重连；未读数以 HTTP 接口为准。
长任务（生成/导入）同步接口 + 任务日志/状态接口超过 3s 的操作用任务进度模式而非转圈；失败给重试入口。
全局响应超时网关响应超时 30s（504）任何请求型交互不要设计成「无限等待」；504 文案引导重试或联系管理员。

5.4 国际化与合规

  • 主应用已支持 zh_CN / zh_TW / en_US / th_TH 四语言，新增文案必须登记 i18n key（system 的 i18n/ 资源）；认证中心暂为硬编码中文，涉及该模块的文案在 PRD 标注 i18n 待补。
  • 账户自助注销（验证码二次确认）是既有合规能力，个人中心设计必须保留。
  • 密码策略（长度 8+、复杂度、90 天有效期、历史 5 次、失败 5 次锁 30 分）可由管理员配置——改密/登录页面要能承接动态策略提示。
