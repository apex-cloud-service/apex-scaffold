## 根本原因分析

### 1. 历史遗留问题

项目最初使用 `mvn` 构建，后来引入 `mvnd` 优化本地开发体验。根据 [CHANGELOG.md](../../../CHANGELOG.md#L213) 的记录：

> "面向用户文档构建命令统一 `mvn` → `mvnd`（Dockerfile 内 Maven 镜像命令保留）"

说明项目已经进行过一次迁移，但**迁移不彻底**，遗漏了多处文档更新。

### 2. 文档维护疏漏

- AGENT.md 更新了构建工具声明和核心构建命令
- 但用户面向文档（README.md、CONTRIBUTING.md、示例文档）未同步更新
- 导致新用户按文档操作时使用 `mvn`，与 AGENT.md 的约定不一致

### 3. 环境差异处理混乱

项目实际支持三种构建环境：
1. **本地开发环境**：应使用 `mvnd`（性能提升 3 倍）
2. **CI/CD 环境**：使用 `mvn`（GitHub Actions 预装）
3. **Docker 构建环境**：使用 `mvn`（官方 Maven 镜像）

但文档中未清晰区分这三种场景的命令差异。

## 总结

### 问题根源

项目在引入 `mvnd` 优化构建性能时，未彻底完成文档迁移，导致 AGENT.md 与用户文档不一致。

### 解决方案

系统性地将所有面向用户的文档中的 `mvn` 命令替换为 `mvnd`，同时明确区分本地开发、CI/CD、Docker 三种环境的构建工具使用场景。

### 预期效果

1. ✅ 文档与 AGENT.md 保持一致，消除混淆
2. ✅ 新用户按文档操作即可享受 `mvnd` 的性能优势
3. ✅ CI/CD 和 Docker 构建流程不受影响
4. ✅ 通过环境差异说明，让用户理解不同场景的工具选择

### 关键假设

1. 用户已安装 SDKMAN 并配置了项目环境（通过 .sdkmanrc）
2. 本地开发环境优先使用 `mvnd` 是合理的性能优化策略
3. CI/CD 和 Docker 环境继续使用 `mvn` 不会影响功能

### 注意事项

1. 修复后需在 README.md 显著位置说明环境准备步骤
2. 对于未安装 `mvnd` 的用户，提供清晰的安装指引
3. 保留 CI/CD 和 Dockerfile 中的 `mvn` 使用，并在注释中说明原因
