# 周期报告（日报 / 周报 / 月报）

> **历史快照**：本文记录某一时点的状态，模块数、端口、路径与类名以当前代码为准，不作为现状依据。

本目录是本工作区所有项目**周期性的过程性报告**的唯一归档位置，按报告类型（而非按时间）建目录，消除此前散落在项目根目录、`reports/2026-10/`、`weekly-reports/` 三处的重复存放。

- [日报](./daily/README.md) - 按自然日记录当日完成、验证结论与风险待办
- [周报](./weekly/README.md) - 按 ISO 周记录本周进展、质量数据与下周计划
- [月报](./monthly/README.md) - 按自然月汇总阶段成果、月度数据与下阶段计划
- [全部项目汇报汇总](./all-projects-consolidated-report.md) - 跨范围、跨周期的单文件视图，含口径差异核对（2026-10-01 至 2026-11-02）

## 一、目录与命名约定

### 1.1 目录职责

| 目录 | 归档粒度 | 周期边界 | 生成时点 |
| --- | --- | --- | --- |
| `daily/` | 自然日 | 当日 00:00–24:00 | 每日 17:00 前 |
| `weekly/` | ISO 周（周一至周日） | 周一 00:00 – 周日 24:00 | 每周六 17:00 |
| `monthly/` | 自然月 | 当月 1 日 – 月末 | 每月最后一天 17:00 |

### 1.2 文件命名

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 日报 | `YYYY-MM-DD-all-projects-daily-report.md` | `2026-11-03-all-projects-daily-report.md` |
| 周报 | `YYYY-Www-all-projects-weekly-report.md` | `2026-W45-all-projects-weekly-report.md` |
| 月报 | `YYYY-MM-all-projects-monthly-report.md` | `2026-11-all-projects-monthly-report.md` |

- **2026-11-03 起为全项目单报告口径**：每期每类报告恰好一份，范围固定为 `all-projects`，覆盖工作区全部项目（apex-scaffold 后端 / apex-admin-web 前端 / cold-chain 冷链），无提交的项目保留条目并说明工作性质，不按仓库拆分多份。
- 同期同类的报告只保留一份，更新即覆盖，不产生 `v2`、`final` 等版本副本。
- 此前按 `<范围>`（apex-scaffold / apex-admin-web / cold-chain / cold-chain-park-supply）拆分的历史报告保留为存档，不再新增按范围拆分的文件。

### 1.3 与《文档与脚本目录结构规范》的关系

[DOCS_STRUCTURE_STANDARD.md](../DOCS_STRUCTURE_STANDARD.md) §1.2 禁止按时间建目录（如 `reports/2026-09/`），§6.1 要求文件名不含日期与版本号。周期报告存在两项**必要例外**，在此显式登记，不视为违反：

1. **不按时间建目录**：本目录严格按 `daily/weekly/monthly` 类型分层，时间只体现在文件名，不形成 `2026-10/` 这类时间目录。
2. **文件名含日期**：周期报告的可区分性依赖周期标识，故 `YYYY-MM-DD`、`YYYY-Www`、`YYYY-MM` 为命名必需部分，不接受省略。

## 二、文件形态约定

| 形态 | 用途 | 是否入库 |
| --- | --- | --- |
| `.md` | **权威源**，唯一索引对象，内容以此为准 | 是 |
| `.docx` / `.doc` | 交付副本，供企业微信、邮件等对外分发 | 是（作为交付物保留） |
| `.html` | 本地渲染副本，供浏览器预览 | 是（作为交付物保留） |

- 三者内容不一致时，以 `.md` 为准，其余形态视为派生件。
- 已入库的历史 `.html`、`.docx` 保留在原处以便追溯，新增报告默认只产出 `.md`；确需交付副本时再单独生成，并在对应 README 登记。
- 项目根目录不应再出现 `daily-report-*.md/html/docx` 散落文件；`.gitignore` 已锚定根目录同名规则，新增周期报告一律写入本目录。

## 三、报告必须包含的要素

自 2026-11-03 起统一为**向领导汇报口径**：结论先行、按项目分条、简明扼要，正文可直接粘贴至企业微信；篇幅约束为**日报约 200 字、周报约 300 字、月报约 500 字**（标题、索引行与月报数据表不计入）。

### 3.1 日报

1. 标题：`# 工作日报（YYYY-MM-DD）`，头部标注覆盖项目与一句话总述（当日重心）。
2. 按项目分条（apex 后端 / 前端 / 冷链）：做了什么 + 解决了什么问题，每条 1–2 句，不写流水账。
3. 验证结论：未执行时显式写「未执行」，不得推断通过。
4. 末行风险与次日切口，一句话。

### 3.2 周报

1. 标题：`# 工作周报（YYYY 年第 ww 周：MM.DD – MM.DD）`。
2. 正文约 300 字：开头 2–3 句总述（本周主要成果、质量结论、遗留问题）；按项目分条，每条不超过 2 句；结尾「下周计划」1–2 句。
3. 本周数据：提交次数、模块或页面数量、测试改动量等可核算指标。

### 3.3 月报

1. 标题：`# 工作月报（YYYY-MM-DD 至 YYYY-MM-DD）`。
2. 正文约 500 字：开头摘要 3 句；按项目分条、按阶段（而非按日流水）叙述；结尾「下月计划」2–3 句。
3. 可附数据表（提交数、模块/页面变化、迁移版本区间），表格不计入正文字数。

### 3.4 数据口径约束

- 提交次数取自 `git log --since --until`，按仓库分别统计并注明仓库名。
- **禁用代码行数（LOC）作为成果指标**：`git log --shortstat` 的插入行数会被 HTML 产物与生成物放大，无法反映真实工作量。改用提交次数、文件数、模块数、页面数、测试类数。
- 构建与测试结论必须来自实际执行结果；未执行则写「未执行」，不得推断通过。

## 四、生成与维护

### 4.1 自动生成

三个周期报告由工作区定时任务产出，写入对应子目录并回写该子目录 README 索引：

| 报告 | 时点 | 数据来源 |
| --- | --- | --- |
| 日报 | 每日 17:00 前（16:45 触发） | 三仓当日 `git log`、`git status`、`.workbuddy/memory/YYYY-MM-DD.md`、`docs/reference/ai-knowledge/` |
| 周报 | 每周六 17:00 | 三仓本周一至周六 `git log`、当周全部日报、`.workbuddy/memory/` |
| 月报 | 每月最后一天 17:00 | 三仓当月 `git log`、当月全部日报与周报、`docs/reference/ai-knowledge/` |

调度规则与生成要点见 `.workbuddy/agents/` 下的报告生成约定；手工补写遵循同一格式。

### 4.2 维护规则

- **每月**：核对三个子目录 README 索引与实际文件是否一致，修正断链。
- **每季度**：将超过 6 个月且无追溯价值的 `.html` / `.docx` 派生副本移入 `docs/_archive/`，`.md` 长期保留。
- 报告不参与技术文档索引，仅在 [项目管理索引](../README.md) 与本目录 README 登记。
