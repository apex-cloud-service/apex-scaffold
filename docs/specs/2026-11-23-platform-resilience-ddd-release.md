# 全仓中台韧性、DDD 与发布能力优化规格

## 背景

本仓库采用 WebFlux、函数式 Handler/Router、DDD 分层与多服务部署，已有缓存、Sentinel、健康检查、Kubernetes 金丝雀清单及网关灰度路由能力。现有能力是否满足目标容量、故障隔离与发布回滚要求，必须以当前代码、有效配置和可运行环境证据核实；不得把配置样例等同于已验证的生产能力。BE-043/FE-029 的全量联调和授权 reader/知识库等遗留仍由原任务承载。本规格对应独立新任务 BE-063，不替代或关闭旧任务。

## 目标

1. 建立覆盖后端模块和部署设施的可追踪架构、风险与容量基线。
2. 在保持现有接口和领域语义的前提下，识别并分批改善 DDD 边界、扩展点和依赖方向。
3. 以证据评估缓存一致性、熔断、超时、重试、隔离、限流、背压及降级策略，避免重试放大、缓存雪崩和级联故障。
4. 明确基础设施可观测、健康探测、配置治理及容量保护的缺口。
5. 核实灰度、蓝绿、负载均衡和回滚链路的真实运行边界，优先验证 Kubernetes；Compose 作为本地兼容回归。
6. 更新受影响文档、脚本、配置和测试，并以实际命令重新生成测试报告。

## 影响面

- 模块：先覆盖根 POM 递归得到的所有后端 reactor 项目，再按证据选定具体变更模块；不假定每个模块都需要改动。
- 接口与数据：默认零 HTTP、消息、数据库和持久化契约变化。若某项优化确需改变接口、DTO、模块坐标、数据库迁移、网关路由或运行拓扑，先独立补充规格、兼容性与迁移方案并获 R3 通过。
- 配置与发布：核对 Spring 配置、Sentinel、缓存、Kubernetes、Compose 与流水线脚本，区分已实现、模板存在、环境未验证三种状态。
- 前端：由独立任务 FE-030 评审 `apex-admin-web`，不得将其变更混入 BE-063；跨仓契约由 R0 串行协调。

## 兼容性

- 保持 WebFlux 与 Handler/RouterFunction；不新增 Servlet 栈或注解式 Controller。
- 保持 DDD 依赖方向和现有服务数据所有权，不把共享设施实现复制进业务库。
- 超时、重试、缓存 TTL、限流阈值等行为变更须依据配置、负载和领域幂等性论证，并有旧行为/新行为回归测试。
- 不用未经验证的默认 SLO 或容量数字作为通过标准。先采集基线，再与业主确认目标；性能测试需记录硬件、拓扑、数据规模和参数。
- 任何灰度/蓝绿方案必须说明流量切换、会话/状态处理、数据库兼容、健康门槛、回滚触发和回滚耗时证据。

## 回滚方案

- 以独立波次和最小文件集实施；每波记录基线 SHA、改动、测试及配置迁移。
- 应用改动按该波次独立 revert；配置/部署变更提供反向配置与流量切回步骤。
- 数据迁移如成为必要前置，另行评审向前/向后兼容和恢复方案；未经批准不执行迁移。
- 发现接口、事务、安全、数据所有权或既有部署语义发生非预期变化，立即停止该波并恢复该波改动，不扩大范围。

## 验收标准

- 后端以根 POM 递归清单覆盖所有模块，结论附代码/配置路径和证据；问题按风险分级，并与 BE-050~BE-062 已登记事项去重或明确关联。
- 每项被实施优化均有对应单测/集成测试，定向 `mvnd -pl :<artifactIds> -am test`、格式检查及适用治理门禁通过；最终按可用条件执行全量 `mvnd -T4 -B clean verify` 并重新生成报告。
- 报告分别列出通过、失败、跳过和未执行；外部服务、凭据、集群、压测环境不可用时不虚报通过。
- 发布能力必须通过静态配置核查及可用环境中的切流/回滚演练；无集群时标为未验证，不以清单存在替代运行验收。
- 独立 R5 复核通过且必改项清零；治理台账、任务、记录、索引和回滚证据齐备后，才可由 R0 申请关闭。
