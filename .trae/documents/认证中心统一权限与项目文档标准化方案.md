# 认证中心统一权限与项目文档标准化方案

## 0. 方案背景与目标

本方案针对用户提出的 5 项整改要求，基于对 `apex-scaffold` 项目的实际代码探查（AGENTS.md 全文、apex-auth-center 全部 Handler/Router/DTO/Domain/Infrastructure、Flyway V44-V54 迁移脚本、主应用权限体系、SSO 模块、三轮子代理调研）制定。核心目标：

1. 补齐代码注释、SpringDoc/Swagger 注解、审计日志、权限控制注解的缺口。
2. 将 **apex-auth-center 确立为全项目统一权限认证与授权的唯一实现**，主应用通过服务调用方式集成，不再维护平行的权限数据与校验逻辑。
3. 修正代码与 Flyway 脚本的字段不一致问题（以代码为准）。
4. 根据代码现状全面对齐文档、脚本、配置、测试代码。
5. 新增架构图、核心业务流程图、时序图等标准化文档。

**关键决策（已与用户确认）**：
- 统一权限认证范围：auth-center 承担全部统一权限认证与授权能力，用到的地方通过接口/服务调用方式集成（不是简单地两套机制并存梳理关系）。
- OAuth2 Handler/Router 的 PMD 作者检查屏蔽：**移除屏蔽并补全** Javadoc/SpringDoc/审计日志。
- 管理端高危操作权限缺口：由本方案给出具体修复设计（见 3.3）。
- 死迁移脚本 `db/migration/auth/`：由本方案根据代码现状给出处理方式（见 3.4，结论：删除）。
- 文档清理范围：包含必要清理（ADR 编号冲突、过时状态描述等），不做大规模目录重组。

**当前实施状态（2026-10-04）**：
- 阶段一已完成：高危管理操作的 RBAC/资源权限校验、MFA 显式租户参数、OAuth2 Handler/Router 文档与审计、DTO/PO 注解及字段说明、对应单元测试与真实 AOP 权限代理测试均已落地。
- 认证中心测试上下文已补齐 `SmsCodeService` 和 `MailService` 的无外部依赖测试替代 Bean；`DualServiceAuthorizationIntegrationTest` 已恢复。

**关于数据模型合并与集成方式的技术决策**：由于用户在后续追问中选择跳过（表示方向已明确，细节由我基于代码判断），以下技术决策基于实际代码约束给出，并在方案中说明理由，供确认：
- 数据模型：采用**主应用表逐步废弃迁移**路径（而非永久并存只读委托），因为"委托但保留原表"会导致双写/数据漂移风险，且与用户目标"auth-center 是唯一实现"冲突；但本方案只做到**设计迁移路径 + 适配层改造**，不做一次性数据迁移脚本的生产执行（数据迁移需独立的、更谨慎的上线计划，且需要实际数据库访问验证，超出本次代码整改范围）。
- 集成方式：采用 **HTTP 远程调用（RemoteApiClient/WebClient）**，而非共享 Jar 包本地调用。理由：AGENTS.md 明确该两个模块"从不共享一个 Spring ApplicationContext"，这是现有架构的强约束（component scan 显式排除）；共享 Jar 包方式需要打破这一约束，影响面远大于用户当前请求范围；HTTP 方式符合 apex-auth-center 作为"独立认证中心服务"的产品定位，且其 9 个 `/auth/v1/*` 接口已经就是为此设计的标准 REST API。
- 现有 `@RequirePermission`/`@DataScope`/`@RequireRole` 注解：**保留注解，替换底层数据源**。理由：27 个 Handler 文件已在使用这些注解，注解本身设计良好（已有 Javadoc、支持 AND/OR 逻辑扩展），全面替换为 auth-center 专属注解体系会导致大范围无必要改动，且违反"不做超出任务要求的变更"原则。只需改造 `RequirePermissionAspect`/`DataScopeAspect`/`PermissionService` 的内部实现，使其通过 auth-center 的权限查询接口获取数据，而不是直接查 `sys_permission`/`sys_role_permission` 表。`RbacMethodSecurityConfig`（Spring Security 原生 `@PreAuthorize`）同理，角色数据来源改为 auth-center。

## 1. 现状分析（Current State Analysis）

### 1.1 两套平行权限体系现状

| 维度 | 主应用（apex-interfaces/application/domain/infrastructure） | apex-auth-center |
|---|---|---|
| 用户表 | `sys_user`（微信 OpenID 体系为主） | `auth_user`（用户名密码 + BCrypt，多租户） |
| 角色/权限表 | `sys_role`/`sys_permission`/`sys_role_permission`/`sys_user_role` | `auth_role`/`auth_permission`/`auth_user_role` |
| 权限注解 | `@RequirePermission`/`@DataScope`（apex-common 定义，`RequirePermissionAspect`/`DataScopeAspect` 在 apex-interfaces 实现，查自己的 sys_* 表） | 自定义 `@RequireResourcePermission` + `ResourcePermissionAspect`（**已实现但从未被任何 Handler 使用，是孤儿机制**） |
| 角色安全 | `RbacMethodSecurityConfig` 启用 Spring Security 原生 `@EnableReactiveMethodSecurity`（`@PreAuthorize` 生效，默认开启） | 无对应机制 |
| JWT/Token | 自己的 `JwtUtil`/`JwtAuthenticationFilter`/`SecurityConfig`，密钥独立管理 | 自己的 JWT 签发/校验、`JwtKeyRotationService`、`KeyManagementService`（AWS KMS/Vault） |
| 模块依赖 | pom.xml 无 auth-center 依赖；全代码库 grep `com.apex.scaffold.authcenter` 零匹配 | 仅依赖 apex-common + apex-infrastructure |
| Spring 容器 | 主应用主类的 component scan **显式排除** `com.apex.scaffold.authcenter..*` | 独立 `AuthCenterApplication.java` 入口，独立容器 |
| 对外 API | — | `/auth/v1/login`、`/auth/v1/logout/{userId}`、`/auth/v1/refresh`、`/auth/v1/permissions/*`（6个端点）、`/auth/v1/roles/*`（7个端点） |

**结论**：这是两套从数据到代码完全独立、零集成的权限体系。要实现"auth-center 是唯一统一权限实现"，必须新增集成层，并逐步收编主应用侧权限判定逻辑。

### 1.2 apex-auth-center 注解与审计缺口（Part 1 核心发现）

- **OAuth2EndpointHandler.java、OAuth2TokenHandler.java 及对应 3 个 Router**（`OAuth2EndpointRouter`、`OAuth2TokenRouter`、`OAuth2MetadataRouter`）：零 Javadoc、零 SpringDoc 注解、零审计日志，且携带 `@SuppressWarnings({"PMD.ClassNamingShouldBeCamelRule", "PMD.ClassMustHaveAuthorRule"})` 主动屏蔽作者检查。覆盖 OAuth2 四种授权类型的 `/token` 端点及 `authorize`/`revoke`/`introspect`，是模块内安全敏感度最高、文档完整度最低的代码。
- 其余 9 个 Handler（AuthConfigHandler、SessionHandler、MfaHandler、RoleHandler、MfaManagementHandler、PermissionHandler、AuditLogHandler、AuthenticationHandler、IpAccessControlHandler）及 7 个对应 Router：Javadoc/SpringDoc 覆盖良好，无需大改。
- **"文档说要校验权限，代码里没校验"的安全缺口**（4 处确认）：
  - `MfaManagementHandler.unlockMfa`：Javadoc 声明需 ADMIN/SECURITY_ADMIN 角色，代码无校验。
  - `SessionHandler.terminateSession`/`terminateUserSessions`：Javadoc 提及 403，代码无校验。
  - `AuditLogHandler.cleanupExpiredLogs`：不可逆批量删除，Javadoc 声明需管理员权限，代码无校验。
  - `RoleHandler.assignPermissions`：批量授权，无任何权限注解。
- 17 个 DTO 文件 `@Schema` 覆盖完整，仅有 `required=true` vs `requiredMode=Schema.RequiredMode.REQUIRED` 的风格不一致（非功能问题）。
- `RolePO`/`UserRolePO` 等 PO 类仅有模板化 Javadoc（`@author Apex Team`），未体现真实提交历史，字段无逐一注释。

### 1.3 Flyway 与代码字段比对结果（Part 3 核心发现）

- **确认无实际问题**：此前怀疑的 `auth_role.dataScope` 不一致，核实后 `RolePO.dataScope` 为 `String`，V45 已将 `auth_role.data_scope` 迁移为 `VARCHAR(32)`，两者一致，**无需修复**。
- **确认死文件**：`apex-auth-center/src/main/resources/db/migration/auth/{mysql,postgresql}/V51__create_auth_center_schema_and_seed.sql`。核实其内容与 V44 高度重叠（同样创建 `auth_user`/`auth_token`/`auth_session`/`auth_permission` 等表），且三个 profile 配置（`application.yml`/`application-dev.yml`/`application-prod.yml`）的 `flyway.locations` 均只配置 `classpath:db/migration/mysql`，从未包含 `auth/mysql` 路径 —— **该脚本从未被执行，是开发过程中的遗留重复文件**。由于 V44 的 schema 已被 V45-V54 持续演进为生产用结构，V51 的 `auth/` 版本已过时且会与现网 schema 产生冲突风险，应**删除**而非激活。
- **V44 文件头注释错误**：`V44__create_auth_center_core_tables.sql` 第 2 行注释写的是"V1__create_auth_center_core_tables.sql"，属于重命名遗留的注释错误，需修正为实际文件名。
- **主应用侧确认问题**：`sys_user_role` 表在 V14/V15 迁移中新增了 `tenant_id` 列，但 `UserRolePO`（apex-infrastructure）及对应 `UserRoleEntity`（apex-domain）均未映射该字段。需核实 `TenantLineInnerInterceptor` 的 `ignoreTable` 配置是否包含该表：若未忽略，则所有新增记录的 `tenant_id` 始终写入 NULL，需补充字段映射；若已忽略，则该列为历史遗留冗余列，需在文档中说明。
- **非问题（确认为合理设计）**：`sys_role.dataScope`在 Domain 层是枚举 `DataScopeType`，PO 层是 `Integer`，通过 `RolePoConverter`（MapStruct）转换，枚举码 1-5 与 V18 的 `CHECK (data_scope BETWEEN 1 AND 5)` 完全匹配，属正确的 DDD 分层转换，非缺陷。
- **非问题（纯风格）**：`DeptPO` 未继承 `BasePO`，而是手动重复声明了相同字段，功能无差异，建议统一但不紧急。
- `apex-auth-center` 的 `auth_user_role` 表（V44 创建）无 `deleted`/`version`/`updated_at` 字段，`UserRolePO` 也未定义，两者一致，非缺陷（设计为关联表，走物理删除）。

## 2. 方案总体设计

### 2.1 统一权限集成架构

```
主应用 (apex-interfaces/apex-application)          apex-auth-center（独立进程/独立容器）
┌─────────────────────────────────┐              ┌──────────────────────────────┐
│ Handler (27个使用@RequirePermission)│              │ PermissionHandler /RoleHandler│
│         ↓ 注解不变                │              │   /auth/v1/permissions/*      │
│ RequirePermissionAspect/           │   HTTP       │   /auth/v1/roles/*            │
│ DataScopeAspect/RbacMethodSecurity  │ ──────────→  │（已存在，本次补齐注解审计）    │
│         ↓ 改造内部实现              │  RemoteApiClient                           │
│ PermissionService                  │              │ PermissionService(authcenter) │
│ （新增 AuthCenterPermissionClient）  │ ←──────────  │ auth_permission/auth_role/    │
│                                     │   权限数据响应 │ auth_user_role                │
└─────────────────────────────────┘              └──────────────────────────────┘
```

**改造要点**：
1. 在 `apex-infrastructure`（或 apex-common，视现有 RemoteApiClient 封装位置而定）新增 `AuthCenterPermissionClient`，封装对 `/auth/v1/permissions`、`/auth/v1/roles/{id}/permissions` 等接口的调用，使用项目既有的 `RemoteApiClient`/`ManagedWebClientFactory` 托管 WebClient。
2. 改造 `apex-application` 的 `PermissionService`：权限数据查询逻辑从直接查 `sys_permission`/`sys_role_permission` 改为调用 `AuthCenterPermissionClient`，结果通过 `MultiLevelCacheService`（L1 Caffeine + L2 Redis）缓存，避免每次权限校验都发起 HTTP 调用。
3. `RequirePermissionAspect`、`DataScopeAspect`、`RbacMethodSecurityConfig` 的角色/权限数据来源同步改为 `PermissionService`（已改造），切面与注解本身不变，27 个 Handler 文件零改动。
4. 用户登录态：主应用的 `JwtAuthenticationFilter` 不改造签发/校验机制本身（避免大范围登录链路改动），但在解析 Token 后查询用户角色/权限时，统一通过改造后的 `PermissionService` 获取——即身份认证（Authentication）暂保持主应用自管，权限数据（Authorization 的数据源）统一来自 auth-center。此为渐进式集成的现实路径，一次性迁移身份认证流程风险过高，不在本方案范围内（见 2.3 分期说明）。
5. 新增 Resilience4j CircuitBreaker 包裹 `AuthCenterPermissionClient` 调用，auth-center 不可用时降级（降级策略：拒绝写操作、只读操作走最后一次缓存结果 + 告警），避免单点故障扩大为全局不可用。

### 2.2 apex-auth-center 自身补齐

1. **OAuth2 相关文件**：移除 `@SuppressWarnings("PMD.ClassMustHaveAuthorRule")` 等屏蔽注解，补齐类级 Javadoc（`@author`/`@version`/`@since`）、方法级 Javadoc、`@Tag`/`@Operation`/`@Parameter`/`@ApiResponse`、`@OperationLog`（敏感字段用 `excludeRequestFields` 排除，参考 `AuthenticationHandler` 已有做法）。
2. **4 处权限缺口修复**：启用模块自带但从未使用的 `@RequireResourcePermission` + `ResourcePermissionAspect` 机制，应用到 `MfaManagementHandler.unlockMfa`、`SessionHandler.terminateSession/terminateUserSessions`、`AuditLogHandler.cleanupExpiredLogs`、`RoleHandler.assignPermissions`。选择理由：该机制已在模块内完整实现（避免引入新设计），且 auth-center 本身就是权限判定的权威来源，使用自己的机制自洽；需补充对应的权限编码种子数据（Flyway seed）与单元测试覆盖这 4 个方法的权限拒绝场景。
3. 其余 DTO 的 `@Schema` 风格统一为 `requiredMode = Schema.RequiredMode.REQUIRED`（替换旧式 `required = true`）。
4. `RolePO`/`UserRolePO` 等 PO 类补充字段级注释，类级 Javadoc 的 `@author` 通过 git blame 查实际提交人（遵循 AGENTS.md 规范）。

### 2.3 Flyway 修复

1. 删除整个 `apex-auth-center/src/main/resources/db/migration/auth/` 目录（mysql + postgresql 两个子目录下的 V51 脚本），因其从未被执行且内容已被 V44+后续迁移覆盖，继续保留只会造成误导。
2. 修正 `V44__create_auth_center_core_tables.sql`（mysql + postgresql）文件头注释中的错误文件名引用。
3. 核实并修复 `sys_user_role.tenant_id` 字段映射缺口：检查 `TenantLineInnerInterceptor` 配置，若该表未被忽略则在 `UserRolePO`/`UserRoleEntity`/对应 Converter 补充 `tenantId` 字段映射；若已被忽略则在相关文档/代码注释中明确说明该列为历史保留字段，不建议新增 Flyway 脚本删除已上线列（避免破坏性变更）。
4. 不新增数据迁移脚本将 `sys_*` 数据灌入 `auth_*`（原因见第 0 节说明，数据迁移需独立评估）。

## 3. 实施步骤与文件清单

### 阶段一：apex-auth-center 自身补齐（Part 1 + Part 2 的模块内部分）

## 4. 验证方式

- 编译与单元测试：`mvnd -pl apex-auth-center,apex-common,apex-infrastructure,apex-application,apex-interfaces -am test`。
- 架构约束测试：`mvnd test -Dtest=ArchitectureTest`（确认新增的 `AuthCenterPermissionClient` 未破坏 DDD 分层规则，确认 apex-interfaces 仍不直接依赖 authcenter 包）。
- Javadoc 检查：`scripts/test/test-javadoc.sh`。
- 代码风格与质量：`mvnd spotless:check`、`mvnd pmd:check`（确认 PMD 屏蔽移除后不产生新的真实违规，若有需要针对性修复而非重新屏蔽）。
- SpringDoc 覆盖核查：对照 `RouterOpenApiCoverageTest`，确认 OAuth2 相关 Router 的 `operationId` 唯一性与文档完整性。
- Flyway 脚本核查：确认删除 `auth/` 目录后 `mvnd -pl apex-auth-center test` 中的 Flyway 相关集成测试仍通过（证明该目录确实未被引用）。
- 集成测试：新增的 `AuthCenterPermissionClient` 调用链路需要 WireMock/Testcontainers 验证正常响应与降级场景。
- 文档核查：人工比对新增/修改文档与实际代码路径、字段、API 是否一致。

## 5. 风险与说明

- **范围较大**：Part 2 的统一权限集成涉及 27 个 Handler 间接依赖的 `PermissionService` 改造，属于高风险的核心链路变更，建议实施时充分的回归测试覆盖，并考虑灰度开关（如 `apex.features.auth-center-permission` 配置项）支持新旧实现并行一段时间后再切换。
- **数据迁移不含在本次范围**：`sys_*` 到 `auth_*` 的实际用户数据迁移需要独立的、与运维协同的上线计划，本方案只完成代码层的集成适配，不执行生产数据搬迁。
- **auth-center 可用性成为新的单点依赖**：主应用的权限校验将依赖 auth-center 服务可用性，需设计好降级与缓存策略，否则 auth-center 故障会放大为主应用权限校验大面积失败。
